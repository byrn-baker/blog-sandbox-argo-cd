# Cluster observability

The root Argo CD Application discovers `apps/08-cluster-observability.yaml`.
This directory owns the additional scrapes, metrics access policies, health
alerts and Grafana dashboard folders. Changes deploy through Git and Argo CD.

| Folder | Contents |
| --- | --- |
| Network | SNMP counters and interface status, generated by `blog-sandbox/telemetry` |
| K3s | Stability overview, control plane, etcd, Linux hosts, pods, workloads and cluster networking |
| Storage | Longhorn volumes and replicas, Kubernetes persistent-volume usage |
| Observability | Argo CD, Grafana, Alertmanager and VictoriaMetrics components |

The existing upstream dashboards are pinned from the previously provisioned
ConfigMaps. `dashboard-provenance.json` records their original names and UIDs.
Their JSON, queries and UIDs are preserved. The chart's dashboard downloader is
disabled; its rule synchronization remains enabled. The sync job prunes its old
dashboard ConfigMaps after this migration. Windows, AIX, macOS, multi-cluster and
Prometheus-server dashboards were omitted because those systems are not deployed.
Review pinned dashboards when upgrading the stack rather than silently fetching
new JSON on every deployment.

Grafana's sidecar reads the `grafana_folder` annotation and creates folders from
those paths. Kustomize provisions one ConfigMap per dashboard. The SNMP generator
sets the Network annotation, including when run with `--dashboard-only`.
Dashboard changes made in Grafana are overwritten by provisioning; edit Git.

## K3s control plane

K3s runs etcd, the scheduler and controller manager inside `k3s-server`, rather
than as standalone Kubernetes pods. Its metrics listeners are on loopback:
2381 for etcd, 10257 for the controller manager and 10259 for the scheduler.
The normal chart Service selectors therefore discovered no targets.

`control-plane.yaml` runs one small vmagent on each master using host networking.
It scrapes localhost every 30 seconds and writes to the existing cluster metrics
store. It neither changes K3s bindings nor restarts the servers. A dedicated
ServiceAccount may only GET `/metrics`. HTTPS certificate verification is skipped
only for the two loopback component listeners; authorization still uses the
projected ServiceAccount token. There are no host filesystem or PID mounts.

K3s shares metric registries between components. Each scrape keeps the relevant
metric families to avoid storing three full copies. Component process metrics
refer to the shared K3s process, not separately isolated daemons. The `instance`
label is the master node name, preserving three distinct targets. Changes to the
scrape ConfigMap reload automatically. Each agent's queue is bounded to 512 MiB
on ephemeral storage; pod replacement can lose queued samples. This is not a
lossless event archive.

The empty chart Service scrapes are removed while their standard alert rules
remain enabled. Extra coverage rules expect three healthy targets for each
control-plane job. Missing agents must not turn into a falsely healthy empty
query.

## Storage and GitOps

`longhorn.yaml` scrapes every manager endpoint on port 9500. Its additive
NetworkPolicy admits only vmagent pods in the observability namespace. Port 9500
also serves Longhorn's API, so this grants that agent access to the shared port,
not URL-level access restricted to `/metrics`.

`argocd.yaml` collects the application controller, ApplicationSet controller,
repository server, API server and notifications controller. Each policy opens
only the selected component's metrics port to vmagent. Redis and Dex metrics
are not included. Application status, reconciliation latency and all component
container restarts are visible in the Argo CD dashboard.

The stability dashboard correlates node readiness, container restarts, API
latency, etcd disk latency and elections, TCP retransmission counters, and volume
health. Longhorn latency is exported in nanoseconds and converted to seconds.
Host TCP counters cannot identify individual failing flows or prove QEMU/GRO
settings persisted. Routing events, packet captures and bounded traffic tests
remain separate evidence. This change does not install VictoriaLogs or network
trap/syslog receivers, or prove external alert notification delivery.

## Validation

Render manifests with `kubectl kustomize observability`. Validate them with
`kubectl apply --dry-run=server --server-side -f <rendered-file>` before pushing.
After Argo sync, verify three control-plane agents, 3/3 targets for each control
plane job, 6/6 Longhorn managers and 5/5 Argo CD components. Query direct etcd
and Longhorn metrics, not just Kubernetes readiness. Check the folder inventory
and rendered dashboard queries in Grafana. Alert rules should load without
errors; a firing alert is investigated rather than removed to make the UI green.
